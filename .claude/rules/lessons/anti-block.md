# Lessons — Anti-block / Signer

Domain lessons for the risk-control and signing surface. Loaded only when files under `mobile/` are in play. Format per `.claude/rules/agent-docs-standards.md`.

- **`data[]` items map to empty records (all fields None).** The search response `data[]` is mixed — most items are videos (`type=1`, wrapped in `aweme_info`, has `aweme_id`) but some are user cards / ads with no `aweme_id`. **Fix:** `mapping.flatten_video` returns `None` for any item lacking `aweme_id`, and `client.unwrap` skips them; never assume `data[0]` is a video.

- **A narrow query returns `502 empty search result (federation_empty)` while the same identity serves other queries fine seconds later.** `search_nil_item: federation_empty` is TikTok's own "the federated search matched nothing" signal — a genuine zero-result, not a shadow-block; `client.py` treats every `search_nil_info` as a soft-reject, so an aggressive `publish_time` window on a niche term is misreported as risk-control. Measured: `Bakıda su` with no filter → 20/20 records on the very device that returned `federation_empty` for the 24h window. **Fix:** `federation_empty` is diagnosed as a real empty result — identity health is judged by whether *other* queries on the same device succeed, never by a single nil response, and a `federation_empty` alone is never evidence of `hit_shark`.

- **The vendored pure-Python signer was written off as "keys frozen at v37" — it works on v46.** The old verdict measured a real failure but named the wrong cause: `signing.py` handed `MetasecSigner` the v32 `ClientConfig` defaults (`app_version 32.9.4`, `sdk_version_code 41090`, `license_id 11512`) while only `RapidSigner` read the `sign_*` v46 values, and `MetasecSigner.sign()` attached no warm identity. Only `DEFAULT_SIGN_KEY` and `GORGON_TABLE` are static in `metasec.py`; the four version fields are arguments to `Metasec.sign`. **Fix:** `MetasecSigner.for_v46()` maps `sign_*` onto those four fields and attaches the warm identity, so `signer: local` signs v46 in-process at zero quota — measured at parity with the paid signer, 15/15 searches and `page_token` chaining included. It holds because `mssdk_ver_code 83952160` is shared between the 37.x and 46.x builds.

- **A stale sign key is silent and imitates stale credentials exactly, so refreshing identities "fixes" nothing.** When TikTok bumps `mssdk_ver_code`, the vendored signer raises nothing — it keeps producing a well-formed signature that risk-control answers with HTTP 200 and an empty `data[]`, which surfaces as `hit_shark`, retires every identity through `report_empty`, and points the operator at credentials that were never at fault. The narrow `TransportError` fallback cannot help: this failure never raises. **Fix:** *all* identities failing at once shortly after a TikTok app release is read as a sign-key symptom rather than a credential one, and the discriminator is flipping one profile to `signer: rapid` and re-running the same query — one paid signature, and the only signal that separates a stale key from stale credentials. RapidAPI stays configured for that diagnostic, not as an answer to empties.

- **A deeply paginated stream can re-serve a record the dedup window has already forgotten.** `paging.py`'s `MAX_SEEN_FINGERPRINTS = 240` is counted in **records**, so its page coverage scales inversely with `limit` — 8 pages at `limit=30`, 4 at 60 — and the module's comment wrongly claimed anything falling off the back could no longer be re-emitted. Measured: a live 15-page user chain served 421 records with **2 duplicates**, re-emitted at 240 and 300 records' distance, i.e. exactly after leaving the window. **Fix:** cross-page dedup is exact only within the trailing window, so a caller that must be globally unique over a deep stream dedupes on its own side; a duplicate beyond the horizon is a known limit of a bounded token, not a pagination defect.

- **Replaying the same `page_token` twice returns different records, so a token is not an idempotency key.** TikTok re-ranks at a given cursor, so a retried continuation yields fresh records rather than the same page. Measured: the same token sent twice returned two 10-record pages with zero overlap. **Fix:** a token identifies a resumable *session position*, not a cached page — retry logic treats a repeated continuation as "more results", never as a safe replay, and nothing caches responses keyed on token identity.

- **Following the API's own `page_token` to the end of a search retires the warm identity, and the caller sees `502` on the last page.** A continuation's empty reply was classified by the sessionless `hit_shark` heuristic, so every terminal "load more" raised `SoftError` and fed `report_empty`; three of them tripped `DEFAULT_STALE_AFTER` and 503'd every caller. **Fix:** a request that carried a `search_id` treats an empty reply as the end of the stream — `200 {count: 0, has_more: false, page_token: null}` in one signed request, not counted against identity health — while a sessionless first page keeps the original heuristic, so invariant (a) still guards the case it exists for.

- **A session tail is an allow-list that fails closed, and it is terminal regardless of `has_more`.** Accepting *any* nil on a continuation let a session launder `hit_shark` into a silent `200 count: 0` that `IdentityStore` never saw (invariants (a) and (b)); separately, trusting a tail reply's `has_more: true` minted an endless chain of empty pages at one paid signature each, and a tail carrying `cursor: 0` rewound the stored cursor. **Fix:** only `empty_session`, `federation_empty`, or an empty page with no nil block at all count as a tail — an unrecognised nil raises `SoftError` → 502 and reports the empty — and a tail retires that endpoint (`has_more=False`) with its cursor clamped monotone, so no token can resume it.

- **A follow-up request with a non-zero `cursor` returns `502 empty search result (empty_session)` on both the local and the RapidAPI signer.** `client.py` `_paginate_into` initialises `search_id = ''` per call, so a fresh HTTP request at `offset > 0` carries no session and TikTok rejects it; the failure is session state, not signing or identity. Measured: page 2 at `offset=10` without `search_id` → `empty_session`, and with the page-1 `log_pb.impr_id` echoed → 13 records, zero overlap, chaining to 35 unique records over 3 pages. **Fix:** cross-request pagination carries the previous response's `search_id` (and TikTok's own returned `cursor`, not `start_cursor + len(records)`, which drifts whenever dedup drops an item) — `search_id` is the resumable session handle and a non-zero offset without it is never a valid request.

- **Region-targeted results come from the query's language, not from the device's `region` fields.** `device_query` claiming `region: US` / `mcc_mnc: 310260` still returns ~100% AZ content for unambiguously Azerbaijani terms, while a cross-lingual homonym (`su problemi` = Spanish "his/her problem") returns ES/IT/MX/BR. **Fix:** search geo-relevance is driven by query language + the account's `store-country-code` + egress IP; there is no `region` query param on `/aweme/v1/general/search/single/`, and per-request mutation of `device_query` region fields is a fingerprint-consistency violation of invariant (c), so region is a per-identity property, never a per-request one.

- **Searches return a silent `200` with `count: 0` and no `hit_shark` warning at all — and the logs look clean.** `client.py` used to derive `self._direct = bool(config.rapidapi_key)`, so a falsy key silently selected the cold legacy `MetasecSigner` **and** disabled the `if self._direct` hit_shark detection — an empty was never raised as `SoftError`. A configuration failure wearing risk-control's clothes. **Fix:** the signer and the direct path are decoupled: `resolved_signer()` drives the mode, `_direct` is true for both `local` and `rapid`, and `signer: local` needs no key — so hit_shark detection is now *on* for a keyless profile and this silent-200 shape is structurally unreachable on `config_direct.yaml`. `create_app` still logs an `ERROR` at startup whenever a keyless profile resolves to the cold `legacy` path, stating that it returns empty by design; that banner is silent in `local` mode, where the premise is false. It carries no key material — its only `%s` args are the config path and the literal env-var name.

- **Swapping the RapidAPI signer provider does not fix empty results.** The RapidAPI signer returns a valid 200 with real `x-argus`/`x-gorgon`; empties come from identity distrust, not the signature. **Fix:** provider switching (`tiktanic` ↔ `working`) is for quota exhaustion only; empty results are resolved by refreshing warm identities, not by changing the signer.
