# Lessons — capture environment (which devices can intercept TikTok traffic)

- **A profile timeout does not prove that the emulator is frozen.** Measured 2026-09-16: `@eduaz2011` still timed out after two app restarts and an emulator reboot, while capture received successful background traffic. The app first called `/aweme/v1/user/uniqueid/?id=eduaz2011`, received HTTP 200 with `status_code: 8196` / `Unique ID is invalid`, and stayed on For You without making a profile request. The addon must capture this resolver rejection under the requested handle so the worker can acknowledge the unavailable page and continue. Only a confirmed rejection is permanent; unknown errors, missing responses, and unreadable bodies remain transient. Inspect resolver responses before attributing repeated timeouts to ANR or capture failure.

Measured 2026-09-10/11 while hunting a `/aweme/v1/aweme/post/` capture. Recorded so these dead ends are not re-run. The GOAL of a capture here is one real request from the app with mitmproxy decrypting it; the barrier is always the same two things — the app must RUN, and its HTTPS must be interceptable (system-trusted CA).

- **A stock x86_64 emulator cannot run TikTok, even with an "arm64 image".** Google's `ndk_translation` (the x86 emulator's ARM bridge, present on API 30 x86_64 images) does not proxy ICU's `ubidi` family (measured: 0 `ubidi` symbols in `libndk_translation_proxy_libicuuc.so`), and TikTok calls `ubidi_openSized_66` at launch → immediate SIGSEGV in `libndk_translation.so`. The APK installs (`primaryCpuAbi=arm64-v8a`) and boots to the launcher; it dies the moment TikTok starts. **Fix:** do not pursue the AVD/emulator route for running TikTok; the translator is structurally incomplete for it. CA install + `-writable-system` + mitmproxy interception WERE all proven working on the x86_64 emulator, so those mechanics are reusable — it is only the app that will not run.

- **Waydroid + `libhoudini` RUNS TikTok, but is not a reliable CAPTURE environment on this machine.** Intel's houdini (installed via `waydroid_script`, needs an Intel CPU; `binder_linux` kernel module; a Wayland session) does proxy ICU, so TikTok 46.9.x launches, loads the FEED, and makes real signed requests — `/aweme/v2/feed/` returns data, `/ms/get_seed` fires, and mitmproxy decrypts it all with the CA installed as a tmpfs overlay on `/system/etc/security/cacerts` (no `-writable-system`, survives no reboot — reinstall after each). BUT: opening a profile by deep-link (`snssdk1233://user/profile/<id>`) hangs in `DeepLinkActivityV2` BEFORE any network request (measured: zero new flows, then an ANR dialog), and under houdini TikTok saturates all cores and adb to the container becomes unresponsive — reproduced across 3+ attempts. So the FEED endpoint is capturable but the POSTS endpoint (which needs the profile screen) is not, on this hardware. **Fix:** Waydroid is good for capturing seed material and feed traffic; it is NOT a dependable way to reach the profile grid. `pm clear` revives a spun-out install (data corruption from repeated ANR/force-stop is what kills it, not houdini per se). Cap the container CPU AFTER the session starts (`/sys/fs/cgroup/lxc.payload.waydroid/cpu.max`, resets on restart) or it takes the host down.

- **The Redmi Note 13 Pro (`emerald`, HyperOS V816) has the Magisk APP installed but is NOT rooted.** Measured: `ro.boot.flash.locked=1`, `vbmeta.device_state=locked`, no `su`, no `/data/adb/magisk`. Magisk-app-present ≠ rooted; without a patched+flashed boot image it does nothing. **Fix:** rooting this phone is a multi-DAY, off-machine operation — Xiaomi mandates a server-side ~7-day (168 h) bootloader-unlock wait after binding a Mi account, the Mi Unlock tool is Windows-only, and unlocking WIPES the device. It cannot be done from this Linux box in a session. On a locked, unrooted Android 15 phone the only in-place interception path is APK repackaging (add a `network_security_config` trusting user CAs, re-sign) — which risks TikTok's `libmetasec` integrity check and is unverified here. The phone renders profiles natively and instantly (no ANR), so once ROOTED it is the clean capture device; until then it is not usable for interception.

- **LDPlayer 14 on Windows RUNS TikTok 46.9.3 and IS a working capture environment (measured 2026-09-14).** Android 14 x86_64 image with `libhoudini` ARM bridge (`ro.dalvik.vm.native.bridge=libhoudini.so`), root via `su` once `basicSettings.rootMode` is on, adb at `127.0.0.1:5555` after `basicSettings.adbDebug: 1` in `vms/config/leidian0.config`. TikTok installs from Play Store, logs in, and opens a profile by deep link (`am start -a android.intent.action.VIEW -d snssdk1233://user/profile/<uid> com.zhiliaoapp.musically`) with NO ANR — the profile fetch (`/tiktok/user/profile/other/v1`) and two posts pages (`/aweme/v1/aweme/post/`, count 9 then 18) fire within ~12 s, unscrolled. **Fix:** the capture stack that works here is (1) mitmproxy CA bind-mounted over BOTH `/system/etc/security/cacerts` and `/apex/com.android.conscrypt/cacerts` and re-mounted into the zygote + TikTok mount namespaces with `nsenter` (`data/setup/install-capture-ca.sh`); (2) `iptables -I OUTPUT -p udp --dport 443 -j REJECT` inside the guest so TTNet's QUIC falls back to TCP/TLS — both are per-boot guest state, re-applied by `data/setup/after-boot.ps1`; (3) mitmdump in plain `regular@127.0.0.1:8890` mode with `adb reverse tcp:8890 tcp:8890` and the guest's `settings put global http_proxy 127.0.0.1:8890` — on this build TTNet DOES honour the Android proxy once QUIC is blocked (measured: every `/aweme/v1/aweme/post/` and profile request of TikTok 46.9.3 arrived through it), so the older "TTNet ignores the system proxy" finding from the Waydroid rig does not hold here. The WinDivert `local:` mode also works but needs an elevated process AND it silently kills the WireGuard tunnel to RabbitMQ (100 % loss while the redirector runs, handshake back within seconds of stopping it), so it is not used. Flows show the server as an IP (`2.20.45.25/...`) because TTNet connects by IP with its own DNS; match on `pretty_host`/`Host`, never on `flow.request.host`.

- **The LDPlayer guest wedges after hours: load average 16–20, `system_server` ANR traces in `/data/anr/`, screenshots stop changing, every `am start` deep link is accepted but never navigates, and the page worker requeues each job with `no profile response within 45s`.** TikTok under `libhoudini` consumes every vCPU the guest has — measured 372 % on 4 vCPUs and 770 % on 8, foreground or background, HOME does not help — so `system_server` starves; memory is not the cause (1.5 GB free of 4). **Fix:** the VM runs with 8 vCPUs / 8 GB (`advancedSettings.cpuCount`/`memorySize` in `vms/config/leidian0.config`; `ldconsole modify` caps at 4) and the supervisor (`data/setup/run-services.ps1`) pins every TikTok thread to cores 0-3 with `taskset -p 0f` and `renice 10` whenever a new app pid appears — host CPU fell from 100 % to ~32 % and the other four cores stay free for the system. The supervisor's watchdog (three harvest timeouts across two or more distinct accounts, no served feed) restarts capture + TikTok and reboots the emulator on every third heal; `install-capture-ca.sh` is idempotent (it unmounts the previous bind mounts before copying, because copying "from" an already-mounted target copies the empty store onto itself and TikTok then distrusts the proxy).

- **A second LDPlayer instance made with `ldconsole copy` registers with TikTok as the SAME device (identical `device_id`, `iid`, `cdid`, `openudid` in both captured identities) — and it STAYS the same after `ldconsole modify --imei/--imsi/--androidid/--mac auto`, a new `ro.product.model`, `pm clear` and a wipe of `/sdcard/Android/{data,obb}/com.zhiliaoapp.musically` (measured twice, 2026-09-17).** TikTok's device registration keys on something the clone shares that none of those touch. Two logged-in accounts on one `device_id` still work in parallel (both resolve profiles and spool posts), but they share TikTok's per-device view and one account's daily search cap. **Fix:** a genuinely separate device is a fresh `ldconsole add` install (Play Store, new TikTok install), never a copy; a clone is acceptable only as a second account on the same device, and its `identities*.json` `device_id` is expected to match the first one's.

- **The keyword worker answers `502 … You have reached the maximum number of searched today.` and, from the same moment, the app on that instance gets a 0-byte `tt_orcas_res: 1` reply from `/aweme/v1/user/uniqueid/` so no profile ever opens.** TikTok's per-account daily search cap reached the app's own handle resolver that day, so the capped account could not serve page jobs either; the cap is account-scoped (a fresh, logged-out instance on the same IP still resolved `@tiktok`). It does not always reach the resolver: measured 2026-09-18 17:33–17:38, `/search` on LDPlayer-2's identity answered the cap message while the same device resolved `@nasa`, spooled its profile and two posts pages a minute later. **Fix:** the consumer takes the LONG backoff on that message and on a 0-byte resolver reply (`STATUS_THROTTLED` → `DeviceThrottled`, status 599), never gives a job up on timeouts, and the page worker keeps running on a search-capped account until its resolver actually answers 0 bytes — only then is the instance paused (`data/services/PAUSE-<name>`) until the cap lifts; capacity beyond ~1500 searches/day per account needs another account on another device.

- **A page job that times out or is throttled and is nacked back IN PLACE returns to the head of the queue; at prefetch 1 with the backoff sleep inside the consumer, one banned or unavailable handle held the whole page queue for 10 minutes (measured 2026-09-17).** Re-queueing in place also re-hammers the same handle every cycle. **Fix:** a device timeout/throttle is re-published at the TAIL of its own queue through the job exchange (`basic_publish(exchange=settings.exchange, routing_key=queue)`) and the original delivery acked; the worker's broker user has no write access to `amq.default` (403 `ACCESS_REFUSED`, measured), so the default exchange is never used. An account whose profile carries no counters (`aweme_count` null; its feed answers `aweme_list: null`) is a banned/unavailable account and is acked with an empty feed at once.

- **TikTok on an 8-vCPU LDPlayer guest ANRs (`Subject: No response to onStartJob`, `Input dispatching timed out`) and the guest shows a black screen with `mCurrentFocus=null` while its load average sits at 25–36.** The 4-core `taskset` fence does not hold: threads TikTok re-creates come back with the full mask (measured: 305 threads, all unpinned, 600–775 % CPU), and once the app is fenced to 4 cores its own UI thread starves among its ~300 threads. **Fix:** the supervisor re-pins every 60 s, and its watchdog (3 timeouts across 2+ handles, no served feed) restarts capture + TikTok and reboots the emulator on every third heal — the pipeline self-heals within ~3 minutes, which is the accepted steady state until a lighter device (a real rooted phone) replaces the emulator. Running TWO such guests on this 20-core host doubles the wedge rate; one emulator serving pages is the reliable configuration today.

- **redroid (Docker Android 13 arm64) on an ARM64 server does not freeze — TikTok 46.9.3 runs native, guest load 0.3–2 with the app open (LDPlayer/houdini: 20–36), a profile visit takes ~10 s, and the app's traffic still egresses from the operator's own connection — but it is NOT the production device, because TTNet's trust in the capture proxy could not be kept stable there (next lesson).** Topology measured 2026-09-18: Oracle Ampere A1 host (`opc@158.101.163.110`, custom `6.12.0-redroid` kernel with binderfs, SELinux permissive, container `tt-00`), SSH tunnel `127.0.0.1:15555 → container 5555`, the Windows box keeps capture/API/workers and `adb reverse tcp:8890` carries the app's proxy traffic back through the tunnel to the local mitmproxy, so TikTok sees the Azerbaijani IP, not Oracle's. Differences from the LDPlayer recipe, each measured: (1) Android 13 has NO `/apex/com.android.conscrypt/cacerts` — only `/system/etc/security/cacerts` is bind-mounted (`data/setup/install-capture-ca-redroid.sh`); (2) the container has no netfilter, so QUIC is blocked on the DOCKER HOST (`iptables -I DOCKER-USER -p udp --dport 443 -j REJECT`, not persistent across host reboots); (3) TTNet advertises `Accept-Encoding: ttzip` on this device and every profile/posts reply comes back `content-encoding: ttzip`, which mitmproxy cannot decode (0-byte bodies) — the harvest addon strips `ttzip` from the request header and the server answers gzip; (4) toybox `pidof a b c` prints nothing when any name is absent, so the CA script enumerates zygotes via `ps -A`; (5) no `curl` in the container — verify the proxy path with `am start -n org.chromium.webview_shell/.WebViewBrowserActivity -d <url>`, which trusts the system store exactly like a well-behaved app. **Fix:** the supervisor instance is `Kind = 'redroid'` (`data/setup/after-boot-redroid.ps1` owns the tunnel, host QUIC rule, CA, proxy, reverse); LDPlayer instances are retired.

- **TikTok on redroid answers `net::ERR_CERT_AUTHORITY_INVALID` (mitmproxy: `client does not trust the proxy's certificate`) for EVERY host through the proxy, keeps doing so after `pm clear`, while the same device's WebView shell trusts the proxy and the CA bytes match in the init, zygote and app mount namespaces.** The trust decision lives in TTNet (Cronet fork), not in the system store, and nothing tried on 2026-09-18 made it stable: a read-only CA store mounted by Docker BEFORE Android init (which replaced the live zygote-namespace remounts, a race of their own) changed nothing; an app-only force-stop/relaunch with the proxy ON broke trust every time; the one sequence that produced fresh captures — container cold boot → app started with `http_proxy :0` and its first TLS connections DNAT'd through a Windows passthrough proxy (`mitmdump --ignore-hosts '.*'`, measured to hand the app TikTok's real DigiCert chain) → proxy ON after 40 s → a fresh profile+posts canary — worked three times in a row on tt-01 (16:18–16:30) and then failed nine consecutive supervisor cycles on both containers (16:34–16:58) with the plumbing measured identical (same iptables, relay up, the Windows public IP on both ends). Restoring the logged-in `/data/data/com.zhiliaoapp.musically` from a tar backup had earlier kept both the login and the trust; app-data state accumulated over repeated cold starts and a server-side TNC change after 16:30 are the surviving hypotheses. **Fix:** a redroid page worker starts only after `verify-trust.py` captured a FRESH profile and a non-empty posts reply through the proxy — a CA fingerprint, a WebView probe or a quiet log is not a trust verdict; `after-boot-redroid.ps1 -Restart` never remounts a live CA store and never runs `pm clear`; the app-data `tar` (`data/backups/redroid-*.tgz`, uid 10077) is the first probe of the next spike; until that spike lands, pages and keywords are served by the LDPlayer rig and the redroid scripts stay parked in `data/setup/oracle-redroid/` (`run-services.redroid.ps1`, `after-boot-redroid.ps1`, `configure-egress.sh`, `transparent-bootstrap.py`, `verify-trust.py`, `TRUST-NOTES.md` — all git-ignored, so they are copied by hand to the VM where the work continues).

- **`adb devices` hangs for minutes — and with it every adb client, LDPlayer's own `adb connect emu:5556` included, and any supervisor loop that calls adb unbounded — while the guest itself is healthy.** Measured 2026-09-18 three times over the SSH tunnels to redroid and once locally against LDPlayer-2, each time on an adb server that an `after-boot` script had started from an agent's tool shell; a server started detached (`Start-Process -WindowStyle Hidden adb start-server`) answered at once and stayed responsive, so the tool shell's console/handle inheritance is the suspect, not proven. **Fix:** the production supervisor runs from the `TikTokSearchServices` scheduled task, every supervisor adb call is bounded (`$AdbTimeoutS`, 25 s) and returns `''` on timeout, the loop never restarts the adb server itself (a `kill-server` from inside the loop wedged it again), and the LDPlayer rig uses only `C:/LDPlayer/LDPlayer14/adb.exe` — a second adb build on port 5037 makes each client kill the other's server. From Git Bash, `adb pull /sdcard/x` needs `MSYS_NO_PATHCONV=1` and a `C:/…` local path, or the remote path is rewritten to `C:/Program Files/Git/sdcard/x`.

- **An account homed in the EU/US region talks to `api32-normal-useastred.tiktokv.eu` (measured 2026-09-18 on the second redroid device), and a capture whose `allow_hosts` and addon host markers knew only `tiktokv.com` passed every one of its requests through untouched — no spool entry, no identity refresh, no error anywhere.** **Fix:** `data/capture/ca*/config.yaml` `allow_hosts`, `capture_identity_addon._TIKTOK_HOST_MARKERS` and `capture_record.TIKTOK_HOST_MARKERS` all carry `tiktokv.eu`, `tiktokv.us`, `tiktok.eu`, `tiktok.us`, and `harvest_spool_addon.http_connect` logs each CONNECT host it does not intercept once (`passthrough (not intercepted): <host>`), so a moved API domain shows up in `capture-*.out.log` instead of as a silent timeout.

- **Every profile visit times out (`no profile entry for handle=… within 45s`, the profile page shows "Something went wrong / Retry") on a guest whose feed loads fine, whose CA is trusted (no TLS warnings in the capture log) and whose authenticated traffic even refreshes `identities.json`.** The supervisor had launched TikTok (via `after-boot.ps1`, which points the guest at the proxy port) BEFORE the capture listener was up, and the app then treated the proxy as dead for minutes: measured 2026-09-18 17:26–17:32 (six visits, two watchdog heals, one manual uid deep link — all failed) against 17:37–17:42 (app started with the listener already up: `@tiktok` by uid, `@nasa` by handle, then every queued page served at ~15 s each). **Fix:** `run-services.ps1` starts the capture, waits, and only then runs the guest setup that launches the app; a watchdog heal keeps the same order (capture up, then `am start`).

- **A guest on the `ca2` capture slot refreshes `mobile/identities.2.json`, which nothing reads, so the keyword path keeps a cookie nobody renews while that guest is logged in and capturing.** `capture_identity_addon` writes `[identity]` (one entry) to its own `identities_out`; `config_direct.yaml` reads only `identities.json`, which the `ca` slot (port 8890, `data/capture/posts`) refreshes. **Fix:** in single-instance mode the running guest, whichever LDPlayer index it is, takes the `ca` slot; two LDPlayer guests at 8 vCPU each starve this host, so one guest (LDPlayer-2, index 1, account 2) is the configuration as of 2026-09-18 evening (`run-services.ps1` `$instances`), and the same account then carries both the keyword search and the page resolver against one ~1500/day cap.
